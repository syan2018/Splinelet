## 文件职责

- `README.md`：范围、依赖、模块边界、任务目录、阶段门槛与分发规则。
- `<序号>-<主题>.md`：一个可独立分发的模块工作包；给出项目背景、上下游和边界，包内用检查点逐项交付/验收，避免每个小步骤都另建执行任务。
- `acceptance.md`：验收映射、证据索引和最终签收。
- 需要冻结跨模块类型时增加 `contracts.md`；设计语义仍引用 `docs/architecture/`，避免两份方案漂移。

架构为什么这样设计放在 `docs/architecture/`；当前产品如何使用放在 `docs/`；分发、进度和验收管理放在本目录；具体测试运行报告放在带实际日期的 `docs/history/qa/`。任务完成后保留原目录并标记已完成；把需要长期维护的行为、接口和架构约定更新到当前文档，不把计划文本冒充当前功能。已有带日期的任务目录作为历史记录保留。

## 管理约定

1. 每个工作包指定负责人，包内检查点指定执行者和验收者，记录起始提交/合同版本；状态以检查点为准，总控不复制一张易漂移的动态状态表。
2. 只在前置交付已签收且写入范围清楚后启动。只读探索可以提前，不可据此绕过合同。
3. 状态使用“未开始、执行中、待验收、返工、阻塞、完成”。阻塞需写明条件、负责解决者及重新开始的条件。
4. 共享文件指定一个整合负责人。多个执行者可以并行开发不相交模块，不能默认共同编辑根组件、公共类型或依赖锁文件。
5. 交付必须包含实际提交、验证命令与结果、验收项映射和未解决问题；验收者签收后才记完成。
6. 合同、范围或依赖变更写进相关子文档和合同记录，标明消费者影响；不在聊天里口头改完就算数。
7. 文档创建不等于任务实施。拟新增的测试命令/文件必须明确标注；未执行项保持待验证。
8. 分发可以给人或独立执行任务；一张工作卡应足以明确上下文和边界，不依赖阅读完整聊天历史。
