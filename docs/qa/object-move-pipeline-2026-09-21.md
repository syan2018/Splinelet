# 对象移动管线验收：2026-09-21

## 环境与输入

Windows，本地开发构建，隔离 Chromium context，1600 × 1100 视口。用户提供的 `output/agent-emblem/sandrone-gold-emblem-v4.spl` 以未绑定副本打开，测试不保存原文件。该文件是本次测量输入，不是测试套件的固定依赖。

常规可复现测试从已提交的 `public/sandrone-example.spl` 出发，通过公开 API 的杯徽配方创建复杂修改器图样。真实文件的图样有 48 段派生曲线；当前配方由源段数量和八重镜像／阵列决定测试预期，不硬编码旧文件的曲线数量。

## 观察与结果

一次实际鼠标移动测量如下。计时包含 Playwright 输入往返，并非 FPS 或跨机器性能承诺；运行时有其他检查负载。

| 阶段                   |  修复前 |  修复后 |
| ---------------------- | ------: | ------: |
| 按下返回               | 1808 ms |  116 ms |
| 连续 30 次移动         |  256 ms |  196 ms |
| 松手返回               | 2315 ms |  268 ms |
| 松手至完整区域结果就绪 | 7024 ms | 5199 ms |

修复后的主页面在选区为空时显示全部 48 段构面输入曲线。按下和移动期间工程身份、文档内容均不变；松手 revision 只增加一次，只有图样部件的 pose 改变，源定义与杯身不变；一步撤销恢复完整文档。

## 根因

- 工程 JSON 约 8.60 MB，其中 Sketch 仅约 0.31 MB；样式、浮雕定义、制造设置及构造输出契约占据主要体积。用简单矩形数量作为唯一性能代理不够。
- 按下即打开模型 preview，触发会话通知、展示投影及额外求值；松手前又发布一个中间 preview，再正式提交。
- 读取编辑状态会重复克隆整份文档。求值通知在没有订阅者时也构造完整结果副本。
- CPU profile 定位到 `projectCreationView → curveModifierAddCapability → analyzeCurveInsertion → evaluateProgram`：原本只是读取“能否添加修改器”，却在主线程重新执行完整构造。
- 画布还会同步计算曲线，而 Worker 已经求出了同一份曲线数据。
- 该旧图样只发布区域。默认“最终曲线”严格读取曲线输出，因此为空；需要明确的 Fill 输入预览，不能伪造发布输出。

## 剩余瓶颈与未采用的试验

完整后台更新仍有约五秒延迟，不能宣称整条管线已经足够快。一次求值快照 JSON 各部分合计约 51 MB：relief 约 21.1 MB、placedRelief 约 11.8 MB、planar 约 12.2 MB，其余包括区域和导出视图。当前任务仍传输完整结果，尚未实现画布专用的精简投影。

曾试验在 Worker 跨 revision 保留现有算子缓存。单独 Node 测量中冷求值约 2162 ms，移动后的缓存求值仍约 2076 ms；浏览器端总等待没有明显改善。该试验已撤回，未把额外驻留内存当作优化成果。下一步应先缩减结果传输及重复身份数据，再设计依赖驱动的增量更新。
